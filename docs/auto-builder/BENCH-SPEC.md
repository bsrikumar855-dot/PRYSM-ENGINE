# PRYSM measurement protocol v1 (normative for M5)

Implements DEC-08 (benchmark definition), DEC-16 (mock model only, no real-LLM claims), A-04, A-09, A-10, A-12, and the DEC-21 replacement of the Cedar differential (see §5). The protocol is fixed **before** any number is produced. Every run's raw output is kept; results are reported even when they miss a hypothesis. Nothing here may be used to claim detection of prompt injection by real models.

## 1. Two kinds of measurement, never mixed
1. **Policy-decision accuracy (deterministic):** labelled `(policy, request, ctx)` tuples against the engine. Because `decide()` is a pure deterministic function, the question is "does policy + engine give the intended outcome", not "does a detector catch attacks". FN = an unauthorised/attack call that the policy **permits** (expected deny, got permit). FP = a legitimate call that the policy **denies** (expected permit, got deny). Rates are reported **per class and overall** with the count, the corpus size and the construction method, plus **Wilson 95% intervals**; no extrapolation beyond the corpus. A result of "0 FN" is stated as "0 of N, 95% upper bound x%".
2. **Performance (non-deterministic):** latency, throughput and overhead, measured on this machine with the protocol of §3, reported as distributions, never as a single number.

## 2. Accuracy corpora
- **Attack/near-miss corpus (exists):** `eval/corpus/*.jsonl`, 563 cases, labelled blind to the code (spec only) by an independent labeller; the engine agrees on all of them (regression pin, not independent evidence of correctness; see DEC-20).
- **Benign set (new):** ≥ 250 legitimate calls for the sample support agent, labelled **by business intent** (what a legitimate support agent does), written by an independent party **blind to the engine and the policy outcome**, covering: documentation search, reading allowed workspace files, emailing corporate addresses with trusted provenance, fetching corporate docs, small discounts with the `sales` scope, varied casing/whitespace/unicode-in-queries, long but legal arguments, boundary values (discount 0 and 10), many distinct workspace paths, nested directories, plus 40+ **borderline-legitimate** calls (e.g. mixed-case paths under case-sensitive roots, optional args absent). Expected effect = permit. Any engine deny is a **false positive**; each FP is then triaged into (a) policy too strict, (b) labeller error, (c) engine defect, never silently dropped.
- **Baselines:** (i) *no guard*: every attack call executes, so FN = 100% by construction (stated, not "measured"); (ii) *prompt-only guard*: **not measured** (owner chose mock-only, DEC-16; a scripted mock cannot say anything about real-model prompt compliance). The report says so.
- **Sample AI application (definition of done):** `examples/support-agent` (§4) — scripted mock model, real sandboxed tools, guard in-process and via the MCP proxy; the benign set's workflows are the sample app's workflows.

## 3. Performance protocol
Record: CPU model, logical cores, RAM, OS, Node version, power plan if detectable, date. Warm-up ≥ 2000 iterations discarded; measured iterations ≥ 10 000 (decide) / ≥ 2 000 (guard/store/proxy); **5 independent repetitions** per workload in separate processes; report per workload: n, median of the 5 per-run p50/p95/p99, min/max across runs and the coefficient of variation; also one **cold** run (first 100 iterations without warm-up). Timers: `process.hrtime.bigint()`. Seeded inputs (fixed PRNG seed recorded). Workloads:
- **W1** `decide()` alone on the 8-rule fixture policy (allow, deny, tainted, invalid args mix).
- **W2** `decide()` with a **200-rule** deterministic synthetic policy (typical + worst-case argument sizes: tiny, 1 KiB, 8 KiB string; 64-element `string[]`).
- **W3** `evaluate()` including request snapshot.
- **W4** guard `call()` end to end with a no-op tool, audit store `synchronous=FULL` vs `NORMAL`, permit path (durable decision row before execution) and deny path (best-effort row).
- **W5** concurrency: 1, 4, 16, 64 concurrent async guard calls on one store (throughput calls/s, p50/p95/p99 latency), plus 4 **processes** appending to one store.
- **W6** proxy end-to-end: a direct client→fixture-server `tools/call` round trip vs client→proxy→server (same fixture), overhead = difference of medians; report both and the number of audit rows written.
- **W7** audit overhead: guard call with the store vs the same call with a no-op in-memory store stub (isolates durable-write cost) — a stub in the benchmark only.
- **W8** report generation time and size for stores of 1k, 10k, 100k decision rows (`prysm report`, `verify-chain`), single run each with RSS.
**Hypotheses to test (not claims):** H1 decide p99 < 1 ms at 200 rules; H2 guard overhead with sync audit < 10 ms p99; H3 proxy overhead < 15 ms p99; H4 `verify-chain` of 100k rows < 30 s. Misses are reported as misses with the likely cause.
Outputs: raw JSON per run under `bench/results/<date>/` (git-tracked, small), a generated table in `docs/auto-builder/BENCHMARK.md`, and the exact commands (`npm run bench`, `npm run bench:quick`, `npm run eval`).

## 4. Sample application requirements (`examples/support-agent`)
A deterministic **scripted mock model** (scenario scripts in code, no network, no model download, no API keys) driving an agent loop that calls tools **only through PRYSM**. Real sandboxed tools writing visible side effects under a temp workspace: `search_docs` (reads a docs folder), `read_file` (workspace), `send_email` (appends to `outbox.jsonl`), `http_get` (local fixture HTTP server on 127.0.0.1 serving canned corp docs), `delete_file`, `set_discount` (ledger file). Policy file = a copy of the fixture policy extended only where the sample needs it. Scenarios (each prints decision ids and the outbox/ledger state): (1) benign flow, (2) unauthorized tool (`delete_file`), (3) forbidden path traversal, (4) retrieval returns a poisoned document → session tainted (`--taint-tools`/`taintsSession`) → exfiltration `send_email` denied, with and without PRYSM (**mock-scripted, unit-level**: it proves the gate, not model behaviour), (5) policy swap → decision explained, (6) store unavailable → fail-closed for high-risk and the fail-open budget for low-risk, (7) the same scenarios through the **MCP proxy** with the fixture MCP server. Each scenario asserts the side-effect state (outbox empty for blocked sends, file still present for blocked deletes). `npm run demo` runs everything and writes a report with `prysm report`. The README states the limits plainly (mock model; in-process vs proxy trust boundary). Measure and record A-09: time from a fresh checkout (after `npm install --ignore-scripts`) to the first blocked call (scripted steps, wall clock).

## 5. Independent second implementation (replaces the Cedar differential, DEC-36)
Cedar was never run (running third-party packages is blocked in this environment, and Cedar cannot express provenance/taint/path/domain predicates anyway). Instead an **independent second implementation** of POLICY-SPEC (decide semantics for tool/args/ctx matching, deny-overrides, taint rule, strictness) is written by an engineer **who has not read `src/core`**, living in `eval/reference/`, and a seeded **randomised differential harness** (`eval/diff/`) generates policies and requests (valid and hostile), runs both, and reports every disagreement (effect or reason_code). Each disagreement is triaged: spec ambiguity (fix the spec, DECISIONS), bug in one implementation (fix), or hostile-input handling difference. The harness runs ≥ 100 000 cases in CI time budget, with the seed printed.

## 6. What the final report must state
Measured values with intervals/distributions; hypotheses met and missed; corpus sizes and who labelled what; the circularity caveat for the 563-case pin; baselines not measured; mock-only limits; Windows-only; single machine; the fact that FN/FP are properties of the **policy plus engine on this corpus**, not detection rates against real attackers.
