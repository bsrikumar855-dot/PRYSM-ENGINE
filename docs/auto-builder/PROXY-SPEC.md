# PRYSM MCP stdio proxy specification v1 (normative for M3)

Implements DEC-01 (enforcing mode), DEC-04 (taint via control config), DEC-07 (schema pinning), A-18. Files: `src/proxy/*.ts` (+ `src/proxy/bin.ts`), tests `test/proxy/*.test.ts`, fixtures `test/support/mcp-server.ts`. Consumes `src/guard` (`createGuardWithAdmin`), `src/store`, `src/core`; no new runtime dependencies (hand-written newline-delimited JSON-RPC; Node built-ins only).

**Threat model.** The agent host (MCP client; may be injected by prompt) talks to PRYSM over the proxy's stdin/stdout. The real MCP server runs as a child of the proxy; the policy file, audit DB and key live where the agent host cannot reach them (deployment duty, documented). **Claim:** PRYSM enforces policy on `tools/call` messages routed through it; it does not stop an agent host that can launch the tool server itself. Only `tools/call` is policy-enforced; all other methods are allowlisted or refused (below). Results from the server are untrusted data.

## 1. Command line
`node src/proxy/bin.ts --policy <file> --db <file> [--key-path <file>] [--agent-id <id>] [--policy-sha256 <hex>] [--taint-tools a,b] [--tool-timeout-ms 60000] [--list-mode hide|show] [--allow-methods m1,m2] [--env KEY ...] -- <server-command> [args...]`
`createProxy(opts)` is the library entry used by tests (`opts.clientIn/clientOut` streams, `opts.spawn(server)` override allowed only for tests). Arguments: policy loaded with `loadPolicy` from bytes read once; `--policy-sha256` (if given) must equal the SHA-256 of those bytes else exit 2 before spawning anything. Server spawned with `spawn(cmd, args, { shell: false, stdio: ['pipe','pipe','pipe'] })`; environment = only `PATH`, `SystemRoot`, `HOME`, `USERPROFILE`, `TEMP`, `TMP` plus names listed with `--env`; never the proxy's own secrets. Bad flags ⇒ exit 2 with a short message (no values).

## 2. Framing & limits
Newline-delimited UTF-8 JSON, one message per line (MCP stdio). Max line 1 MiB from the client, 4 MiB from the server (excess ⇒ client side: JSON-RPC error `-32600` with `id` null and the oversized line is discarded; server side: the corresponding pending call fails with `-32603` and the event is audited as `tool_error`). Invalid JSON ⇒ error `-32700`, `id: null`. A JSON array (batch) ⇒ `-32600`. Non-object ⇒ `-32600`. Messages must have `jsonrpc: "2.0"`. Client request ids may be numbers or strings; ids beginning with `prysm:` are reserved ⇒ `-32600`. Proxy-originated requests to the server use string ids `prysm:<n>` and their responses are consumed by the proxy (never forwarded).

## 3. Method policy (client → server)
Always handled/forwarded: `initialize` (forwarded; the response is returned unchanged except `capabilities.tools.listChanged` is kept as is), `ping`, `notifications/initialized`, `notifications/cancelled`, `notifications/progress`, `tools/list`, `tools/call`. **Everything else** (`resources/*`, `prompts/*`, `completion/*`, `logging/*`, `sampling/*`, `roots/*`, unknown methods) ⇒ JSON-RPC error `-32601` unless the method is listed in `--allow-methods`, in which case it is forwarded unmodified and documented as **not policy-enforced**. Notifications (no `id`) for refused methods are dropped. Server → client messages (server-initiated requests such as sampling, notifications, log messages) are forwarded unchanged; server-initiated `roots/list`/`sampling/createMessage` are forwarded as the server sent them (documented: PRYSM does not police server → client traffic).

## 4. tools/list
After the downstream `initialize` response is relayed and the client sends `notifications/initialized`, the proxy sends its own `tools/list` (paginating through `nextCursor`, max 20 pages / 2000 tools) to the server and builds the registry: for every server tool `t` (name must match `^[A-Za-z0-9_.:-]{1,64}$`, otherwise it is ignored and an `audit_skipped`-style sink line is written) compute `definition_hash = sha256(JCS({name, description, inputSchema}))`. A tool is **exposed** iff it exists in the policy `tools` **and** (the policy tool has no `schema_hash` **or** it equals `definition_hash`). Mismatch ⇒ hidden, calls denied as `unknown_tool` publicly, and the audit row carries `outcome.reason = "schema_changed"`. Tools not in the policy are hidden when `--list-mode hide` (default) or listed but still denied when `show`. The registry is installed with `admin.setTools` (audited `tools_replaced`); on `notifications/tools/list_changed` from the server the proxy refreshes (re-fetch, re-hash, `setTools`) and forwards the notification only if the exposed set changed. The client's `tools/list` is answered **by the proxy** from the filtered cache (`{ tools: [...] }`, original definitions of exposed tools, no cursor); if the cache is not ready yet the proxy waits (max 10 s, then `-32603`).

## 5. tools/call
Request `params: { name: string, arguments?: object, _meta? }`. Invalid shape (name not string, arguments not a plain object when present) ⇒ result `isError: true` text `Blocked by PRYSM: invalid_request (decision <id>)` after a **best-effort audit row via the guard path** (use `guard.call` with the name coerced to string only if it is a string; otherwise call the guard with the sentinel name `"?"`). Flow: `guard.session(sessionId).call(name, arguments ?? {}, { })` where the registered tool function forwards `{ method:'tools/call', params:{ name, arguments: <frozen snapshot args>, _meta } }` to the server under a fresh proxy-side request id and resolves with the server's `result` (a JSON-RPC `error` from the server ⇒ throws → `tool_error`). **The arguments forwarded to the server are exactly the snapshot args the guard hands the tool function — never the client's original object**; `_meta` is passed through only `progressToken` (string|number), nothing else.
Responses to the client (same `id`): permit + server result ⇒ the server's `result` unchanged (untrusted). Guard blocked ⇒ `result: { isError: true, content: [{ type:"text", text:"Blocked by PRYSM policy: <denied|unknown_tool|invalid_request|unavailable> (decision <decision_id>)" }] }` — no rule ids, no policy version, no argument values. `tool_error` ⇒ `isError: true`, text `Tool error (decision <id>)`; `tool_timeout` ⇒ `isError: true`, text `Tool timed out (decision <id>)` and the proxy sends the server `notifications/cancelled` for the forwarded request. A single session per proxy process (random id, `guard.session()`); `--taint-tools` names (must exist in the policy) are registered with `taintsSession: true`: after a **successful** call to such a tool the session is tainted, so later external-effect tools are denied by core. Client `notifications/cancelled { requestId }` for an in-flight `tools/call` aborts the guard's tool signal and forwards a cancellation to the server (the client still gets exactly one response for that id: a `tool_error`-style result or the server's response, never two).

## 6. Lifecycle & failure
- Client stdin EOF ⇒ abort in-flight calls, close the server's stdin, wait ≤ 2 s then kill it, `guard.close()` (writes the anchor sink line), exit 0.
- Server exits/crashes ⇒ every pending request fails (`tools/call` ⇒ `isError` result `Tool error`; others `-32603`), the proxy writes `{"prysm":"proxy_server_exit","code":...}` to stderr, `guard.close()` and exits 1. Writes to a dead server must not throw uncaught.
- stderr of the server is forwarded to the proxy's stderr unchanged; PRYSM sink lines (JSON, §AUDIT-SPEC 4.16 shapes plus `proxy_*` lines) go to stderr as well. **stdout carries only protocol messages.**
- Uncaught exception ⇒ sink line `{"prysm":"proxy_fatal"}` (no message/stack content), kill the server, exit 70. A fail-closed default everywhere: if the guard or store fails, calls are blocked as `unavailable`.
- Concurrency: many in-flight `tools/call`; responses may complete out of order; ids are mapped correctly; a response for an unknown id from the server is dropped with a `proxy_orphan_response` sink line.

## 7. Required tests (acceptance evidence for A-18; use a **real child process** MCP server fixture written in this repo, `test/support/mcp-server.ts`, speaking newline-delimited JSON-RPC, with tools that record every invocation to a side-effect file)
1. **A-18:** forbidden call (policy deny, unknown tool, schema-pin mismatch, tainted external-effect) ⇒ the **server-side counter file stays 0** and the client gets the blocked result; the allowed call increments it exactly once and returns the server result.
2. Arguments received by the server equal the guard snapshot (NFC-normalised, frozen content) — test with an NFD string and with a client that sends `__proto__`/extra keys ⇒ blocked, server counter 0.
3. Prompt-injection scenario (scripted, unit-level — owner chose mock only): a tool result containing instructions is returned, a `--taint-tools` retrieval tool taints the session, the subsequent attacker `send`-like call is denied; the same call before taint is permitted.
4. Method policy: `resources/list`, `prompts/get`, unknown method ⇒ `-32601`, server never receives them; `--allow-methods resources/list` forwards it.
5. tools/list filtering (hide mode), schema pin hide + call denied, `tools/list_changed` refresh with audited `tools_replaced`, pagination, invalid tool names ignored.
6. Framing: invalid JSON, batch array, non-object, oversize line, reserved `prysm:` id, duplicate in-flight ids.
7. Lifecycle: client EOF shuts everything down with an anchor line; server crash mid-call; hung tool + `--tool-timeout-ms` ⇒ `tool_timeout` and a server-side cancellation notification; client cancel ⇒ exactly one response.
8. 20 concurrent calls out of order with distinct args ⇒ correct id mapping, audit rows match.
9. Audit: decision rows precede execution (server-side file timestamps vs store seq), `verify()` ok, no argument values in the DB/WAL/stderr (canary), agent-visible text contains no rule ids/policy version.
10. CLI: bad flags exit 2; `--policy-sha256` mismatch exits 2 without spawning; env allowlist (a canary env var in the proxy process is not visible to the server).

## 8. v1.1 amendments (DEC-27; from the blind M3 test plan W1–W22). These supersede earlier text where they conflict.
1. **Host identity (W1).** New flags `--user-id <id>`, `--scopes a,b`, and repeatable `--provenance arg=label` (label matching the provenance regex). All are **host-supplied, never read from the client**; they populate the guard ctx on every call (`userId`, `scopes`, `provenance` for the named argument names). `--provenance` is a host *assertion* about an argument that the client controls — documented loudly as dangerous (use only when the host really controls the value), and each use writes a `{"prysm":"proxy_provenance_asserted","arg":"<name>"}` sink line at start. Default: no scopes, no user, no provenance ⇒ fixture tools requiring provenance (`send_email`) are unreachable through the proxy **by design** (the proxy cannot know where an argument came from); tests use `--scopes sales` for `set_discount` and `http_get` for the taint demonstration.
2. **One block string (W2).** All blocked results (incl. invalid shape): `Blocked by PRYSM policy: <denied|unknown_tool|invalid_request|unavailable> (decision <uuid>)`.
3. **allow-methods (W3).** Entries must match `^[a-z][a-z0-9_]*(/[A-Za-z0-9_/-]+)?$` exactly (literal, no wildcards, no empty entries, no spaces); an entry equal to any always-handled method (`initialize`, `ping`, `tools/list`, `tools/call`, `notifications/initialized`, `notifications/cancelled`, `notifications/progress`, `notifications/tools/list_changed`) ⇒ exit 2 before spawning. Forwarded allow-listed requests are forwarded as a **canonical re-serialisation of the parsed object** (never raw bytes), with duplicate top-level keys rejected at parse time (`-32600`).
4. **Oversize server line (W4).** Discard to the next newline (buffer capped); since it cannot be attributed, **fail every pending request** (`tools/call` ⇒ `isError` result `Tool error (decision <id>)`; others `-32603`), write `{"prysm":"proxy_server_exit","code":null,"reason":"oversize"}`, kill the server, `guard.close()`, exit 1.
5. **schema_hash / list fields (W5).** Policy `schema_hash` is lowercase 64-hex (no prefix); anything else (or uppercase) is a mismatch ⇒ tool hidden/denied. The listed definition is rebuilt from the whitelist `{name, title, description, inputSchema, outputSchema, annotations}` (other keys, including `_meta`, dropped). Hash covers only `{name, description, inputSchema}` (documented: other fields are unpinned). New flag `--require-pins`: tools whose policy entry has no `schema_hash` are hidden/denied.
6. **Not ready (W6).** `tools/call` arriving before the registry is ready waits up to `readyTimeoutMs` (flag `--ready-timeout-ms`, default 10000, library option), then is blocked `unavailable`.
7. **Registry failures (W7).** Initial build failure ⇒ empty registry (everything `unknown_tool`), retried on the next client `tools/list` (at most 1 retry/s) and on `list_changed`. Refresh failure ⇒ keep the last good registry (never widen), sink line `{"prysm":"proxy_registry_refresh_failed","reason":"..."}`. A failed `setTools` audit append counts as refresh failure.
8. **Duplicates (W8).** A tool name appearing more than once in the server list is hidden entirely (`proxy_tool_ignored`, `reason:"duplicate"`).
9. **Server → client traffic (W9).** Classified by shape. (a) Server responses (`id`, `result|error`, no `method`) are matched **only** against the pending map; unknown/duplicate ⇒ dropped, `{"prysm":"proxy_orphan_response","kind":"server"}`. (b) Server-initiated **requests** (`method` + `id`) are **refused by default**: the proxy answers the server with `-32601` and writes `proxy_server_request_refused`; opt-in `--allow-server-requests m1,m2` forwards those methods (documented unenforced). (c) Server **notifications**: forward only `notifications/progress` whose `progressToken` belongs to an in-flight proxied call, and a proxy-synthesised parameterless `notifications/tools/list_changed` (after a registry swap that changed the exposed set); everything else dropped unless `--allow-server-notifications` is set. (d) Client **responses** (no `method`) are forwarded only for an outstanding forwarded server request id; otherwise dropped with `proxy_orphan_response` `kind:"client"`.
10. **Caps (W10).** Max 64 in-flight proxied `tools/call` (excess ⇒ JSON-RPC error `-32000` for that id, sink line `{"prysm":"proxy_busy"}`, no row); max 64 waiters for readiness; `list_changed` refreshes coalesced (≤1 running + 1 queued); `progressToken` string ≤ 128 chars or number, else `_meta` omitted; stdout backpressure: pause reading the server's stdout while the client output buffer is full until `drain`.
11. **Duplicate in-flight id (W11).** Respond `ERR(null, -32600)` and keep the original call untouched. Ids `1` and `"1"` are distinct; numbers beyond 2^53 are compared by their parsed double.
12. **tools/call as a notification (W12).** Dropped, never executed (sink line optional).
13. **Cancellation (W13).** Only a tracked in-flight proxied `tools/call` is cancelled: the client `requestId` is translated to the proxy-side id and a `notifications/cancelled` is sent to the server; untracked ids (unknown, completed, denied, `prysm:*`, `initialize`) are ignored and never forwarded. The client always gets exactly one response per id. Extra `params` keys on `tools/call` are dropped (only `name`, `arguments`, `_meta.progressToken` are forwarded).
14. **Taint on dispatch (W14).** For `--taint-tools`, the proxy's tool wrapper calls `session.taint()` **when the call is dispatched** (after the permit decision is durable, before waiting on the server) so errors, timeouts and `isError` results also taint. Residual (documented): calls already decided in parallel, and a proxy restart resets taint.
15. **initialize (W15).** Forwarded; the response's `capabilities` is rewritten to `{ tools: { listChanged: <true if the server set it> } }` only (so refused methods are not advertised); `serverInfo`, `protocolVersion` and `instructions` are kept. A second `initialize` ⇒ `ERR(id, -32600)`. `ping` is answered locally with `{}`.
16. **Framing details (W16, W17).** Split on `0x0A` only; `\r` is JSON whitespace; blank lines ignored; a UTF-8 BOM at stream start ⇒ `-32700`; invalid UTF-8 ⇒ `-32700` (fatal decoding); a partial final line at EOF is discarded; envelope errors (`-32600`) echo the `id` when it is a string or finite number, else `null`; the 1 MiB limit is inclusive and excludes the newline; any `JSON.parse` exception (including stack overflow from deep nesting) ⇒ `-32700`, never a crash.
17. **Server output shapes (W18).** Non-JSON or non-object lines from the server are dropped with a `proxy_orphan_response` `kind:"server"` line; a response with neither `result` nor `error`, or with both, or a `result` that is not an object ⇒ `tool_error`.
18. **Exit codes & startup order (W19).** Order: parse flags → read policy once → verify `--policy-sha256` → open store (key mismatch/unwritable DB) → create guard → spawn server. Exit **2** for any usage/policy/hash/db/key error (before any spawn); exit **3** if the server cannot be spawned (e.g. ENOENT; no path/command text printed); exit **1** server exit/crash/oversize/stdout-closed; exit **70** fatal; exit **0** clean shutdown.
19. **Server stderr (W20).** Every line of server stderr is forwarded to the proxy's stderr prefixed with `[server] ` so operator log parsers cannot be spoofed by `{"prysm":...}` lines. Documented: the server child runs as the same OS user and is **outside** the protection scope for the DB, key and policy files (run the server as a different account/sandbox for that).
20. **Sink shapes (W21).** `{"prysm":"proxy_tool_ignored","reason":"bad_name"|"duplicate"|"schema_changed"|"not_in_policy"|"no_pin","n":<count>}` (counts only, never names), `proxy_orphan_response{kind}`, `proxy_server_exit{code,signal?,reason?}`, `proxy_registry_refresh_failed{reason}`, `proxy_server_request_refused`, `proxy_busy`, `proxy_provenance_asserted{arg}`, `proxy_fatal`; all single-line JSON, values sanitised ≤ 64 chars, never raw tool names/args/paths/ids.
21. **Test seam (W22).** Library option `readyTimeoutMs` (and the flag) so tests do not wait 10 s.

## 9. v1.2 amendments (DEC-28; M3 gate pass 1: security-engineer M3-01..06, critical-reviewer MAJOR-1..3 + minors, black-box QA deviations). Supersede earlier text where they conflict.
1. **Client → server data channels (M3-01).** Client `notifications/progress` are **dropped** unless `--allow-server-requests` is non-empty; when forwarded, `params` is rebuilt as `{ progressToken, progress, total }` (numbers only, `progressToken` per item 2). `initialize` params are rebuilt from a whitelist: `protocolVersion` (string ≤ 32), `capabilities: {}`, `clientInfo: { name, version }` (strings ≤ 64, else defaults); `_meta` and every other key dropped. `progressToken` (in `_meta` of calls and in progress notifications) must match `^[A-Za-z0-9_.:-]{1,64}$` or be a non-negative safe integer, else it is omitted.
2. **Output escaping (M3-02).** Every serialised line written to the client or the server escapes U+2028, U+2029 and U+0085 as ` `, ` `, `\u0085` (valid JSON, same parse) so line-splitting readers cannot desynchronise.
3. **Large results (MAJOR-1).** `--max-server-line-bytes` (default 16 MiB, max 64 MiB; client line cap stays 1 MiB). An oversize server line is **discarded** (buffer capped, framing resynchronises at the next newline); every pending `tools/call` fails closed with an `isError` result `Tool error (decision <id>)` and its id is marked abandoned (late replies dropped with `proxy_orphan_response`), other pending request kinds get `-32603`; the proxy writes `{"prysm":"proxy_server_oversize"}` and **keeps running** (it neither kills the server nor exits). §8.4 is superseded. An oversize client line is answered `-32600` with `id: null` (documented: unattributable).
4. **Windows launch & cleanup (MAJOR-2, M3-06).** A synchronous spawn throw maps to exit **3** (`spawn_failed`, no command/path text). On Windows the proxy kills the server **process tree** (`spawnSync('taskkill', ['/PID', String(pid), '/T', '/F'])`, fixed binary, args array) on shutdown paths; elsewhere `kill`. `bin.ts` installs SIGINT/SIGTERM handlers that run the same shutdown path as client EOF (abort, close server stdin, grace, kill tree, `guard.close()` writing the anchor line, exit 0). `.cmd`/`.bat` shims are unsupported with `shell:false` (documented: launch `node <script>` / the real executable). The environment allowlist additionally includes, on win32 only, `ComSpec`, `PATHEXT`, `windir`, `SystemDrive`; anything else via `--env`.
5. **Guard-routed rows for unexposed tools (critical minor, M3-03).** The proxy no longer writes its own deny rows. `GuardAdmin` gains `denyUnexposed(toolName: unknown, reason: "schema_changed"|"no_pin"|"tool_not_offered"|"not_ready")` (src/guard edit allowed for this item): it writes a best-effort decision row through the guard's `pre_evaluate` budget and `dropped_before` accounting, with `effect: deny`, `enforcement: "enforced"` **regardless of policy mode**, `reason_code` `unknown_tool`, `tool` = the name only if an own policy key else `"?"` + `outcome.tool_hmac`, `outcome.reason`, and returns `{ decision_id }`. `admin.setTools(registry, meta?)` accepts an optional `meta` object whose integer/short-string fields (≤ 64 chars, ≤ 8 keys; nested `hidden: { reason: n }` allowed) are merged into the `tools_replaced` row's `outcome` (the proxy passes `{ exposed_n, hidden: { <reason>: n } }`).
6. **Truncation (minor).** A tool list truncated by the 20-page/2000-tool caps or by a total 8 MiB list-size cap writes `{"prysm":"proxy_tool_ignored","reason":"truncated","n":<count ignored or 0>}`.
7. **Timeouts & ordering (minor).** `forwardRequest` for `initialize` and allow-listed methods has a timeout (`--forward-timeout-ms`, default 30000) after which the client gets `-32603` and the pending entry is released. The tools/call shape check happens **before** waiting for readiness.
8. **Server stderr (M3-04).** Forwarded lines: control characters (except tab) replaced by `?`, U+2028/2029/0085 escaped, length capped at 1000 characters, always prefixed `[server] `.
9. **Pins (M3-05).** At startup a policy tool without `schema_hash` writes `{"prysm":"proxy_unpinned_tools","n":<count>}` (counts only); documented that pins cover list-time `{name, description, inputSchema}` only.
10. **Flag validation (QA/minor).** `--agent-id`, each `--scopes` entry: `^[A-Za-z0-9_.:-]{1,64}$`; `--user-id`: same pattern ≤ 128; empty CSV entries in `--taint-tools` and `--env` ⇒ exit 2 (consistent with `--allow-methods`/`--scopes`); `--provenance arg=label` requires `arg` to be declared by at least one policy tool else exit 2.
11. **Envelope handling (QA).** Whitespace-only lines are ignored like blank lines; a message with an `id` but without `method`, `result` or `error` ⇒ `-32600` echoing the id; a late server reply to a timed-out/cancelled call ⇒ `proxy_orphan_response{kind:"server"}` (once per id).
12. **Backpressure (MAJOR-3).** While the client output buffer is full the proxy pauses **both** the server's stdout **and** the client's stdin until `drain` (listener re-armed on error/close; no unbounded `clientOut` growth from proxy-generated replies).
13. **Audit posture rows (M4 usability).** At startup the proxy appends (durable, via `admin`) a `policy_activate` row with `outcome.event = "proxy_config"` carrying `{ list_mode, require_pins, tool_timeout_ms, taint_tools_n, allow_methods: [<grammar-valid names>], allow_server_requests: [<names>], allow_server_notifications, provenance_args: [<names>], scopes_n, user_set }`; after `initialize`, a best-effort `policy_activate` row `outcome.event = "proxy_client"` with sanitised `clientInfo` `{ name, version }` (≤ 64 chars each). The `monitor_only` policy mode is allowed (the proxy enforces nothing different: guard semantics apply) and the `proxy_config` row records `policy_mode`.
14. **Required additional tests.** Backpressure with a non-reading client stream (server stdout paused, proxy replies bounded; mutation-kill the pause); `setTools` failure (fault-injected store) keeps the last good registry and writes `proxy_registry_refresh_failed`; `--provenance` through the real CLI; a `monitor_only` policy through the proxy (hidden tool still blocked, row `enforced`); exit 70 via the test seam; waiters cap (64) and refresh coalescing; client progress/initialize extras never reach the server (`methods.jsonl` assertion); U+2028/2029/0085 round trip through a readline-based fixture; oversize server line keeps the proxy alive and only fails pending calls; sync spawn throw ⇒ exit 3; SIGINT/SIGTERM (where testable) ⇒ anchor line; Windows process-tree kill with a wrapper that spawns a grandchild (assert no survivor); hidden-tool flood shows `dropped_before` on the next row; truncated list sink line; whitespace-only line ignored; id-only message ⇒ `-32600`; stderr sanitising (ANSI/CR/U+2028).

## 10. v1.3 amendments (DEC-30; M3 gate pass 2 residuals). Supersede earlier text where they conflict.
1. **Exit code 3 through the CLI.** `ProxyConfigError` with code `spawn_failed` (synchronous spawn throw, e.g. `npx.cmd` EINVAL on Windows) exits **3** from `bin.ts`; every other config error stays 2. CLI test (win32 only; skipped elsewhere) with `npx.cmd`.
2. **Stuck client (M3-12).** If the client output buffer stays full (no `drain`) for longer than `--client-stall-ms` (default 30000; library option `clientStallMs`), run the shutdown path (abort pending, close server stdin, grace, kill tree, `guard.close()` anchor line) and exit 1 with `{"prysm":"proxy_client_stalled"}`. A paused stdin that never ends must not keep the proxy alive.
3. **No test hook in production (M3-13).** Remove `PRYSM_PROXY_TEST_FATAL` from `bin.ts`. The exit-70 path is exercised through the library `fatal()` seam only; that test asserts the **fixture server pid is gone** afterwards.
4. **Oversize result blast radius (M3-11).** Behaviour stays "discard the line, fail all pending calls, keep running"; every failed call's proxy-side id is added to `abandoned` (spec §9.3 wording); documented in the README ("one oversize result fails concurrent calls; raise `--max-server-line-bytes` or avoid huge outputs").
5. **proxy_config list caps.** `allow_methods`, `allow_server_requests`, `provenance_args` are limited to 32 entries each at flag validation (exit 2 beyond), so the posture row never exceeds the store's JSON column cap.
6. **Activation lookup.** The guard decides whether to append a startup `policy_activate` row by scanning back (at most 50 rows) for the newest `policy_activate` row **that has `outcome.policy_version`** (rows with `outcome.event` of `proxy_config`, `proxy_client`, `tools_replaced` and similar are skipped), so restarts do not write redundant activation rows. M4 consumers must filter on `outcome.event`.
7. **denyUnexposed after close.** After `guard.close()`, `denyUnexposed` writes no row and returns a decision id only.
8. **Test additions.** `test/guard/v14.test.ts` asserts `tool_hmac` equals the guard's keyed HMAC of the raw name and that the raw name is absent from the DB for a non-policy tool name; a proxy-level test sends a raw non-policy tool name through the not-ready path and asserts the same; a stalled-client test (never-draining output) ends in bounded-time shutdown with exit 1.
